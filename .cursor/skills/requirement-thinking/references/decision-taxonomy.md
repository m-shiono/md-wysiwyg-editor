# Decision Taxonomy

要件整理で「誰が決めるか」を分類する。メインセッションは **Class U** のみユーザーに質問する。

## Class U — User（ユーザーが決める）

ビジネス価値・方向性・優先度に関わる判断。技術的正しさはユーザーに委ねない。

| 例 |
|----|
| 対象ユーザーと解く問題 |
| MVP スコープ（In / Out） |
| 料金モデル・収益方針 |
| データ保持期間のビジネス要件 |
| コンプライアンス・法規制の既知制約 |
| 期限・予算の上限 |
| パネル対立時の優先順位（例: コスト vs セキュリティ） |

## Class A — Advisor default（専門家パネルが決定）

ベストプラクティスに沿った技術判断。ユーザーは異議がなければ採用、覆す必要はない。

| 例 |
|----|
| 認証方式の実装パターン |
| API 設計スタイル（REST / RPC 等） |
| ログレベル・構造化ログ |
| キャッシュ戦略 |
| デプロイ・ロールバック手順 |
| 監視メトリクスの初期セット |

## Class B — Blocked（パネル対立 → ユーザーへエスカレート）

技術的に複数の正当な選択肢があり、ビジネストレードオフが必要なときのみ Class U として質問する。

| 例 |
|----|
| リアルタイム必須 vs コスト最小 |
| オンプレデータ必須 vs マネージド SaaS |
| 完全オフライン vs 常時クラウド同期 |

## メインセッションの禁止事項

- Class A についてユーザーに質問しない
- パネル未実行のまま技術推奨を単独で出さない
- `requirements-agent` の Raw 出力をそのままユーザーに貼らない

## ID 付与規則

| Prefix | 意味 |
|--------|------|
| `UD-NNN` | User Decision（未決 → Phase C で質問） |
| `AD-NNN` | Advisor Default（確定、異議で覆す） |
| `RK-NNN` | Risk（情報提供のみ） |
